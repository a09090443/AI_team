## 同一討論串操作

在原討論串 **@主機器人**（不是只 tag PM 角色）：

- `處理 #1011`：讓等待人工的舊任務交由 PM 分析。
- `補充 #1011 你的答案`：把實際回覆帶入 PM 問題處理。

- `中斷 #1017`：只停下目前這一輪（與執行中狀態訊息上的「中斷這一輪」按鈕相同）。

只允許白名單使用者、原頻道與原討論串，且必須已有 QA 計畫與 QA 結果。
佇列採原子狀態轉換，重複請求不會重複派工。不新建任務或重建工作區。
Slack 會區分「已排隊」、「PM 處理中」、「已派工」與「等待你回覆」。

### 需求本身有問題（2026-09-25）

- 新任務：測試計畫受阻會先交給分流（`plan.blocked = "triage"`）。分流判定是需求問題時用 route=requirements，
  並附 `human_decision`，停止訊息出現「核准：…」按鈕，負責人按下即核准該變更。
- 需求整理規則：只寫產品可觀察的行為；版本追溯、commit 差異、稽核、計畫覆蓋等流程證據由系統負責，不得寫成需求。
  不得自行刪除難以驗收的需求，但真人核准的變更要求刪除時照做並記錄。
- 任何任務（含舊快照）：停在測試計畫且已有需求基準時，停止訊息提供「需求要改」，
  需求負責人可直接送 `補充 #<ID> 核准需求變更 <要怎麼改與原因>`；系統回到需求節點重訂基準，
  之後設計、計畫、實作、驗收、審查照常重跑，計畫與 PR 仍需核准。非負責人或尚無基準時回白話說明。
- 「中斷這一輪」之後 runtime 交回的結果一律不採用（Codex 被停時可能以結束碼 0 交出半成品）；寫入範圍稽核照常執行，
  越界等安全例外不會被當成中斷而掩蓋。

### 承接時有未提交的修改（2026-09-25）

任務用完次數時，工作區可能留有「有寫檔權、沒有 commit 權」的角色（例如 LIMITED 驗收補的測試）的修改。
承接只帶走已 commit 的內容，所以停止訊息會列出這些檔案，並提供「保存未提交的修改並承接」：
系統先以工作區身分把它們 commit 到原任務（停用 repository hooks），再建立承接任務；新任務照常重新驗收與審查。
- 按鈕綁定訊息貼出當下的內容指紋；之後內容又變動就拒絕，請送 `補充 #id 狀態` 看最新清單。
- 保護路徑（`project.protectedPaths`）與 `.git` 一律不代為保存，請管理者處理。
- 只有驗收負責人可以操作；audit 記錄檔案清單與新 commit。

使用者操作被拒時，Slack 只顯示白話原因（`Diagnostics.forUser`）；例外類別與呼叫脈絡寫在 audit。

### 中斷這一輪 vs 中止任務（2026-09-25）

| | 中斷這一輪 | 中止任務 |
|---|---|---|
| 入口 | 執行中狀態訊息的按鈕，或 `中斷 #id` | 停止訊息／核准卡上的紅色按鈕 |
| 停掉的程序 | 該任務的 agent（`ai-team-<id>-*`）與系統驗證（`ai-team-check-<id>-*`） | 同左（先前版本只改狀態，程序會繼續跑） |
| 任務狀態 | `AWAIT_HUMAN`，可續跑 | `ABORTED`，終止；重啟時刪除工作區 |
| 次數與 session | 本輪已計次不重扣；「繼續執行」沿用原 session | 不適用 |

只接受配置流程中正在執行的任務；排隊、等人、角色對話與舊版管線任務會回覆說明、不做事。
中斷時 agent 若已交出結果，結果照常採用，停在下一步開始前。被停掉的驗證不會被當成程式失敗交回實作。
中斷旗標只存在記憶體，只對當下這一輪有效。

## 恢復與紀錄

`task_remediation` 保存目前階段、修正輪數與指示；`stage_attempt` 保留新增的每次階段產出，
原有 `stage_result` 仍保存最新一份。舊結果不會追溯補成歷次紀錄。
用量中斷走原有 checkpoint／繼續按鈕，續跑當前修正階段。
服務重啟時，執行中或排隊中的問題處理會停止並明示等待人工，不默默重跑。
若原工作區或 QA 稽核基準缺失，停止而不重建取代現場。
