# ADR：受阻責任自動交接與驗收前系統證據

- 日期：2026-09-14
- 狀態：Accepted
- 決策者：AI Team 維護者與需求提出者

## 背景

配置式流程原本以節點與全流程次數上限阻止循環。當 QA 或 Reviewer 已提出可執行、
且明確指向配置內責任角色的缺陷時，若接手節點的歷史次數已達上限，流程仍會停住，
只能由真人反覆辨識與恢復。測試計畫也可能寫出 QA 當下沒有操作契約可執行的指令，
使權限缺口直到驗收階段才被發現。

## 決策

1. 受阻報告必須保留來源節點、原因、證據與配置路由；系統據此建立不可重放的交接鍵。
2. 只有配置中既有的 `blocked`／`routes` 目標可自動接手。即使一般節點或流程上限已達，
   每個任務仍可處理最多 6 個獨立受阻事件；同一事件可通過最多 12 個節點，避免正常的
   「分流→修復→重驗→審查」耗盡事件額度，也防止同一證據無限循環。歷史計數不重設。
3. 人工恢復授權優先；`human`、需求變更、計畫核准與 PR 核准一律停止等待真人。
4. 測試計畫的每個情境必須引用管理者宣告的 `operation_ids`。規畫角色會看見對應
   verification 節點的操作契約；未知、未授權或重複的 ID 由確定性閘門拒絕。
5. v2 流程在 QA 前先於全新 clone 執行管理者固定的獨立驗證。QA 與 Reviewer 共用同一份
   綁定 HEAD、需求基準及配置版本的收據；產品或驗收階段重做時收據失效。
6. LIMITED 驗收節點留下未提交變更時，只有 diff 全部位於其 `writablePaths` 且不含保護路徑，
   才能依 blocked 分流節點的 `implementation` route 自動交給 WORKSPACE 實作節點提交。
   系統不放寬驗收 runtime 的 `.git` 權限；無唯一安全路由時停止給真人。
7. 有效的系統獨立驗證收據是固定完整建置操作的主要證據；QA 不得因自己的操作清單沒有
   重複列出同一命令而宣告受阻，但仍須核對其餘情境證據。
8. 第一版曾以 `證據:節點:次數` 逐次計算交接，既有快照在讀取執行時會將同一證據的舊 key
   合併為一個 `incident:` 事件並留下稽核紀錄。只有全部舊 key 都可辨識時才降低計數；未知
   格式保留原本較高值，避免遷移時意外放寬防循環限制。
9. 六個事件用完後，停止訊息會提供綁定目前配置、受阻證據與 HEAD 的一次性授權碼。只有原
   驗收負責人可核准，每次增加兩個事件，額外額度硬上限為六；相同現場不可重放。這不重設
   `visits`、`transitions`、事件歷史、需求／計畫核准或 PR 閘門。
   配置遷移會使舊配置的額外額度失效，但保留已使用 token 與事件歷史。
   2026-09-25 修正：延長以「目前已用事件數」為基準再加兩個，總上限仍為 6+6=12。舊做法在
   既有額外額度上加二，遷移後已用數高於上限時要連按數次才會真的放行（#1017）；延長一次
   已無法再多放行任何事件時不再提供延長，改提供承接新任務。

## 未採方案

- 全面提高或清空原上限：會隱藏真正的流程循環，也破壞既有稽核語意。
- 所有受阻都交真人：安全但會讓已有明確責任與路由的修復無謂停擺。
- 讓 agent 自由指定命令或角色：會繞過管理者配置的權限與流程邊界。
- 只把全域上限改大：會延後真正循環的停止時間，且無法修正舊制逐節點重複計數。

## 影響

新任務能在有限預算內自行完成「發現缺陷 → 分流 → 修復 → 重驗 → 審查」。無法確認責任、
需要擴權、改需求／計畫核准，或交接預算耗盡時仍會停止並由負責角色簡要說明。
舊快照不會被改寫；其既有 `blocked` 目標可在真人再次續跑時重建一次交接證據。
