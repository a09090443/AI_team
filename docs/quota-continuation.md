# 額度暫停與人工續跑

## 2026-09-10 更新：Codex 措辭與遠期解禁

兩家供應商的措辭不同，處理方式也不同（實測樣本，非推測）：

| 供應商 | 原文 | 有時區？ | 排程 |
|---|---|---|---|
| Claude | `You've hit your session limit · resets 6:30pm (UTC)` | 有 | 該時刻加 2 分鐘 |
| Codex | `You've hit your usage limit. … try again at Sep 15th, 2026 1:09 PM.` | **沒有** | 見下 |

Codex 只給日期時刻、不給時區，換算成任何時區都是猜測，猜錯會白等或提早撞牆。
因此 `QuotaRetryTime` 只取邊界不取值：最早解讀為 UTC+14、最晚為 UTC−12。
當「連最早解讀都在 24 小時之後」（`farBeyondBackoff`），就改排在最壞解讀之後
試一次，中間不再每 6 小時重試；重試路徑沿用同一判斷，不再無條件加 6 小時。
兩者皆無法解析時才退回原本的 30 分鐘起退避。

Slack 訊息由 `QuotaMessage` 統一呈現，兩個時間分開講、不混為一談：

```
任務 #1014 等待額度。
供應商指定解禁：Sep 15th, 2026 1:09 PM（原文照登，未標時區，系統不推測）
下次自動嘗試：2026-09-16 09:11（台北時間）
```

供應商時間一律原文照登（標了 `(UTC)` 才不加註）；只有我方排定的時間才換算台北並
格式化為 `yyyy-MM-dd HH:mm`。修正前這裡是 `ZonedDateTime.toString()` 的原始輸出，
且解禁時間埋在英文 JSON 裡，實務上等於看不到。

事故背景：#1014 於 2026-09-09 遇到 Codex 用量上限，解禁在六天後，
舊邏輯以 6 小時退避反覆重試，預期會空轉約 24 次。

## 2026-09-08 更新：自動續跑

已新增 session limit 辨識與 quota_retry 持久化排程。以下 2026-09-05 內容為歷史紀錄；
新版 WAITING_QUOTA 在具備明確額度原因與 checkpoint、提出者仍在白名單且沒有
需求變更待核准時，自動透過既有中央佇列續跑。一般 AWAIT_HUMAN 不自動執行。

明確 `resets 6:30pm (UTC)` 格式以错误發生時間換算，重置後加 2 分鐘；
未知時區／格式從 30 分鐘退避（60、120、240、最長 360 分鐘）。
排程每 60 秒檢查一次。首次建立排程在 Slack 原串回報台北時間；
到期只嘗試原工作，不以額外模型呼叫探測配額、不購買或兌換額度。
再次遇到額度上限才安排下一次；其他失敗遵循原本人工處理流程。
排程時間不代表供應商已恢復。任務中止、結束或白名單移除即不再自動排隊。

quota_retry 保存觀察時間、下次嘗試與次數；程序重啟保留等待時間。
已經排隊或執行中的 v2 任務若遇到服務重啟，仍沿用原保守政策等待人工，
不重播可能已執行的動作。手動繼續與自動排程共用原子狀態領取。
新表由完成啟動恢復後明確初始化，不使用 ApplicationReadyEvent，因 Slack
主連線會阻塞 CommandLineRunner。

#1014 僅依使用者授權與保存的 is_error/session limit 證據改為 WAITING_QUOTA；
原 session、工作區、需求及角色快照保留。首次排程為台北 2026-09-09 02:32。
這不是將歷史 AWAIT_HUMAN 任務批次改為自動續跑。

驗證：173 項測試中 170 通過、3 項 opt-in smoke 略過；check-source 與 16 項
平台 fixture 通過。真實配額恢復後的完整續跑尚待到期觀察。

## 歷史：人工續跑

2026-09-05：新增 WAITING_QUOTA／RESUME_QUEUED 與 Slack「繼續任務」。

只有供應商的錯誤欄位明確出現 usage_limit_reached、insufficient_quota
或已辨識的額度耗盡文字，才判定為額度問題。一般 429、逾時、網路錯誤，
以及 agent／工具輸出中引用這些文字，都不據此認定額度耗盡。
重置時間不自行推算；原始錯誤有提供時直接呈現，否則未知。

每次執行前將角色、runtime、要求的模型、上游脈絡、QA 初始 commit 存入
task_checkpoint。Claude 預先產生 --session-id 並先存入資料庫；Codex 從
thread.started 取得 ID 後立即保存，無須等最終結果。模型原本為空字串時
仍代表 CLI 預設，不代表已取得實際模型名稱。

額度耗盡時停止下游、釋放執行槽、保留原工作區與未提交修改，並在原討論串
tag PM／提出者。續跑不呼叫 WorkspaceManager.provision、不清除現場；
已驗證的上游階段沿用原報告，從中斷階段接續。QA 仍使用第一次進入 QA 前
的 commit 作越權檢查基準，不能漏掉中斷前的修改。

「繼續任務」使用 SQLite 條件更新，只允許 WAITING_QUOTA 轉為 RESUME_QUEUED；
連按、重送或中止後的舊按鈕不重複派工。服務重啟後 WAITING_QUOTA 繼續保留，
尚未執行的 RESUME_QUEUED 退回 WAITING_QUOTA，等待人再按一次，不自行重試。

沒有 session ID 時會明確通知，改以保存的需求與上游脈絡啟動同一階段的新
session。CLI 明確回報已辨識的 session 不存在訊息時，通知後只嘗試一次新
session 接手；其他錯誤保持待查，不自動改 runtime、模型或權限。
續跑 prompt 要求先核實 git status／log／未提交變更，禁止先清除現場。

每次重試前，原 stdout／stderr 改名為 .previous-UUID 保留，不被覆蓋。
「重新開始」與續跑不同：重新開始先將舊工作區移到與 workspaces 同層的
workspace-archives，再建立乾淨 clone。封存失敗則停止，不刪掉舊內容。
封存不由工作區啟動清理掃描，需日後明確決定保留期限。

PR 仍須所有階段驗證通過與人工核准。這版沒有自動排程重試、額度購買、
reset 兌換或跨 runtime 接手，也沒有修復 #1010 的沙箱初始化問題。

驗證：SQLite 持久化／冪等 DDL／重複領取，假子行程的 session 早期捕捉，
額度正反例、續跑同一 QA 階段／原始基準／禁止重新 clone，以及遺失 session
接手時保留要求的 runtime／model。未刻意耗盡真實訂閱額度。
