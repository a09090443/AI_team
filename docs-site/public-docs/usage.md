# 操作與角色對話

日常操作優先使用任務訊息上的按鈕；需要文字輸入的按鈕會開啟輸入視窗。
按鈕與文字指令都經白名單、原頻道、原討論串及任務狀態檢查，不會繞過核准。

## 常用指令

下列指令在原任務討論串 @主 App 使用，`123` 請換成實際編號。

| 指令 | 用途 |
|---|---|
| `補充 #123 狀態` | 在 AWAIT_HUMAN／WAITING_QUOTA 時唯讀查看狀態與選項；其他狀態會回覆不能續跑 |
| `補充 #123 檢視測試計畫` | 查看測試計畫 |
| `補充 #123 檢視完整報告` | 查看完整階段報告 |
| `補充 #123 <答案>` | 回答等待中的問題，沿原任務快照繼續 |
| `處理 #123` | 將等待人工的任務交 PM 分流分析 |
| `中斷 #123` | 停止目前執行輪次，保留任務供後續繼續 |
| `開 PR #123` | 由任務提出者要求發布；仍須符合狀態與證據閘門 |

核准需求變更、測試計畫與 PR，以及承接新任務，限任務提出者。其他指令也受各自的狀態與權限檢查。

## 容易混淆的按鈕

| 按鈕 | 效果 |
|---|---|
| 繼續執行 | 在允許續跑時沿原任務繼續，不自動套用新配置 |
| 中斷這一輪 | 停止目前程序，轉為等待人工，保留任務 |
| 中止任務 | 終止任務；工作區會在下次服務重啟清理 |
| 改用新任務繼續 | 從已提交成果建立新任務，使用目前配置，不沿用核准；基準分支的新程式要到實作階段才併入，要從最新程式開始請送新需求 |
| 保存修改並改用新任務繼續 | 先保存可歸責且允許提交的修改，再承接 |
| 重新進入核准 PR | 重新檢查並顯示核准卡，本身不推送 |

以目前訊息實際提供的選項為準。不要複製其他任務的核准碼或按鈕。

## 直接向角色提問

管理者為角色建立獨立 App 並啟用直接 mention 後，可以在允許頻道使用：

```text
@QA Agent 這個需求還缺哪些驗收情境？
```

一般文字是唯讀對話，即使寫「幫我改」也不會直接實作。明確派工須使用「執行 」前綴：

```text
@Backend Agent 執行 補齊 README 的啟動說明並驗證
```

新討論串的派工交中央流程；v2 既有任務在 `AWAIT_HUMAN`／`WAITING_QUOTA` 時依原快照與節點續跑，仍受目前人工閘門限制。legacy 才交 PM 分流，要求 `AWAIT_HUMAN` 且已有 QA 計畫與結果；不符合會拒絕。
角色對話不取代 QA、審查或發布核准，也不會自動讀取整個 Slack 歷史與未記錄附件。
角色未建立獨立 App 時由主 App 代發，無法直接 @該角色。
