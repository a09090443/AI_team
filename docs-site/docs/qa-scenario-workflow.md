# QA 情境導向流程

本文件描述產品開發流程；部署既有服務可走 [服務建置](service-delivery.md)，由 Infrastructure 建置後檢查，不先進 QA 計畫。

流程：PM →（需要時 Architecture）→ QA 測試規劃 → Backend → QA 驗收 → Code Reviewer → 人工 PR 核准。
沿用 PM 的 QA 路由判斷；無 Backend 的分析／詢問任務不進實作流程。

QA 規劃在 Backend 與工作區建立之前，以需求和既有契約設計情境，不接收本輪 Backend 報告。
新任務先把每項需求拆為具 ID 與維度的原子驗收項目，再建立需求 × 操作／角色／輸入 ×
成功／失敗／邊界 × 執行機制的覆蓋矩陣。每個情境包含穩定 ID、需求與原子驗收 ID、
前置條件、資料、方法、步驟、預期結果、環境需求、`operation_ids` 及 `counterexample`。
`counterexample` 必須描述一個會通過弱測試但違反需求的實作，並說明本情境如何攔下它。
每個 `operation_id` 必須是管理者配置給對應 verification 節點的契約；
測試規畫不得只在文字中自行發明命令。契約不足時要明確受阻，不把權限缺口留到 QA 才發現。

**系統內建的 `inspect-content`**（2026-10-03 起，所有 v2 配置自動可用，不需配置）：以 QA 自己的 Read／Grep
讀工作區中**已提交**的檔案內容判定。它不是指令，不經派工前檢查、不寫檔。只適用於「從檔案內容就能判斷」的驗收項目
（文件文字、設定值、檔案是否存在、表格結構）；程式行為仍須引用真正的操作，缺操作仍要受阻。驗收時 `command` 寫
`inspect-content：<檔案>:<行或範圍>`、`evidence` 引用讀到的內容；系統同時在驗收上下文附上「本次已提交的變更檔案」
（`WorkspaceManager.changedPathsSinceBase`，系統查得）。配置不能自行宣告同名操作（`OperationContract.INSPECT_CONTENT`）。
起因：只改一行文件的任務，任何配置都寫不出「讀某檔某行」的固定指令，任務永遠卡在測試計畫。

**系統內建 `compare-unchanged-files`**（2026-10-10 實作，部署狀態見交接紀錄）：驗證指定既有檔案未被修改。
計畫在情境的 `operation_ids` 引用此 ID，`unchanged_paths` 填 1–100 個明確的 repo 相對檔案路徑；
不使用它的情境填空陣列。計畫 schema 由執行期擴充，舊計畫沒有此欄位仍可讀取。不得填目錄、萬用字元、
絕對路徑、`..`、`.git` 或控制字元；中文與空白檔名可用。不是 agent 的 shell 指令，不增加角色權限。

系統在工作區建立／承接時將當下 Git commit 保存為 `comparisonBase`，返工不更換；
只有系統把新的基準合併進任務分支時（實作前同步、PR 衝突同步）改為新基準 commit，基準帶進來的變更不算本任務修改，
見 [工程流程](engineering-workflow.md#實作前同步最新基準2026-10-24)。
獨立驗證在建置前以 Git 物件比較指定檔案的內容與模式，包含純文件略過建置的情況；
修改、刪除、改名或檔案型別變更會失敗，沿既有受控流程交回實作修正。
基準缺失、基準不存在的檔案、基準為目錄／symlink／子模組，則明確停止，不以目前 HEAD 補造基準，也不假裝通過。
比對針對兩個已提交版本，不代表中途從未改過或還原過，也不比較建置產物或被忽略的檔案。

QA 使用系統收據 `fileComparison` 的逐檔結果、版本與紀錄路徑作為證據，不需要自行跑 Git。
發布前檢查收據綁定目前 HEAD、需求、配置、完整計畫、比較基準與路徑清單，並核對比對紀錄雜湊及內容。
`baseline_revision` 是**需求內容雜湊**，不是 Git commit，不能拿來做程式差異比對。
這項能力不會自動新增或刪除需求，也不保證模型列出的路徑完整；計畫覆蓋與程式審查仍須核對使用者要求。
已配置且釘選 SHA256 的固定 bash 腳本可引用操作 ID；例如 repo 的漂移掃描腳本可提供實作與驗收使用。
未配置的腳本仍不可自行發明操作，見 [跨專案契約](cross-project-execution.md)。需求來源與驗收文字矛盾時先核對，不以刪除檢查掩蓋缺口。
缺少必要需求決策時向 PM／提出者回報並停止。READY 只代表計畫就緒，不代表環境已驗證。

`qa_plan` 與 `qa` 各自持久化 stage_result、session、診斷 log 與費用。
兩階段共用 QA Slack 帳號，不需新 token；runtime 與模型在配置式模式由團隊 JSON 的測試角色決定，
legacy 模式用 `AI_TEAM_MODEL_QA`／`AI_TEAM_RUNTIME_QA`。

Backend 取得計畫，交付實作、單元測試、啟動方式、環境與限制。
QA 依原計畫逐情境執行，回報實際結果、操作及證據。讀碼僅供定位，不能取代行為驗證。
QA 仍可新增測試，不可修改產品程式碼、pom 或既有測試斷言；原沙箱與 git 路徑稽核保留。
Code Reviewer 負責程式審查，並取得原測試計畫以查核驗收證據。
對 v2 任務，系統會在 QA 前先用全新 clone 執行固定的獨立驗證；QA 與 Reviewer
只能核對綁定目前 HEAD、需求基準與配置版本的收據。後續修改產品或重做驗收會使收據失效並重跑。

發布閘門拒絕缺少計畫、空情境、重複／未知／遺漏需求或原子驗收 ID、缺少反例、
非 PASS、缺少證據、HIGH 問題、
未核實事項。人工核准及佇列發布前也重新核對，不能略過。
判斷在 `QaGate`：驗收報告的 `uncertainties` 非空就擋，不區分是不是需求基準早已約定「本環境無法核實」的項目。
自動流程不會放行；2026-10-08 起驗收負責人可以用 `開 PR #<id>` 明確放行（其他條件必須全過），PR 說明會列出這些事項，
審查還沒跑時先補跑審查，見 [review-gate](review-gate.md#放行未核實事項補跑審查2026-10-08)。
在那之前，專案 `testInstructions` 若要求「需要 PostgreSQL、外部 API 金鑰的情境一律標為無法核實」，就與這道閘門互相矛盾：
驗收情境全數 PASS，仍以「QA 仍有未核實事項，禁止發布」停下，負責人只好結案。
這是結構完整性檢查，不能單憑非空 log 字串證明 agent 沒有捏造證據；仍需獨立審查。

額度暫停沿用 WAITING_QUOTA 與人工繼續：QA 規劃可續原 session，尚未建立實作工作區；
Backend 或 QA 續跑沿用原計畫，QA 保留最初的 commit 稽核基準。
舊任務若沒有 qa_plan，不能事後補寫計畫冒充事前規劃或直接發布，須重新開始完整流程。
既有 v2 任務保留建立時的 schema 與 prompt，可沿用舊欄位續跑；新規則不會竄改歷史計畫。

自動化測試使用模擬 runtime，不代表 agent 在真實任務中產出的情境計畫品質已被驗證。

## 文件任務的相稱驗收（2026-10-12 來源更新）

純文字修正可合併相同行為的驗收項目，以來源、新值、應消失的舊值與必要一致性查核，不為湊矩陣而增加無關情境。
文件站需依本專案固定操作在隔離副本建置；實作先準備快取，QA 離線驗證，不能以實作自陳替代。
SQL、腳本與設定驗證相關行為；真正要求從零安裝成功則須有實際建置／啟動證據。文件作者為實作角色，QA 不代改產品文件。
既有計畫、驗收、審查與核准節點保留，沒有基於模型自陳的跳關。

plan schema 新增必填 `protected_path_changes`（至多 100 個明確相對檔案，無則 []），只列需求確實要修且需跨 runtime 改派的檔案。
計畫禁止與情境 `unchanged_paths` 衝突；唯讀參考、目錄、glob、危險路徑不能用來授權改派。
系統從實作節點前置計畫取得清單，提交前以 Git 核對實際檔案，不再以文字提及判定；細節見[配置流程](configurable-team.md)。
