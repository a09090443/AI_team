# 額度暫停與自動續跑

## 什麼算額度用盡

只有供應商的錯誤欄位明確出現 `usage_limit_reached`、`insufficient_quota`、session limit
或其他已辨識的額度耗盡文字，才判定為額度問題。一般 429、逾時、網路錯誤，
以及 agent／工具輸出中引用這些文字，都不據此認定額度耗盡。

額度耗盡時任務轉為 `WAITING_QUOTA`：停止下游、釋放並行槽、保留原工作區與未提交修改，
並在原討論串通知。額度停止不呼叫錯誤說明 agent（同帳號額度已用完）。

## 續跑時保留什麼

每次執行前把角色、runtime、要求的模型、上游脈絡、QA 初始 commit 存入 `task_checkpoint`。
Claude 預先產生 `--session-id` 並先存入資料庫；Codex 從 `thread.started` 取得 ID 後立即保存，不必等最終結果。
模型為空字串代表 CLI 預設，不代表已取得實際模型名稱。

- 續跑不重新 clone、不清除現場；已驗證的上游階段沿用原報告，從中斷階段接續。
- QA 仍以第一次進入 QA 前的 commit 作越權檢查基準，不會漏掉中斷前的修改。
- 續跑 prompt 要求先核實 git status／log／未提交變更，禁止先清除現場。
- 每次重試前，原 stdout／stderr 改名為 `.previous-UUID` 保留。
- 沒有 session ID 時會明確通知，改以保存的需求與上游脈絡啟動同一階段的新 session。
  CLI 明確回報 session 不存在時，通知後只嘗試一次新 session 接手；其他錯誤保持待查，不自動改 runtime、模型或權限。

## 自動續跑排程

`QuotaAutoResume` 每 60 秒檢查一次。任務符合下列全部條件才會自動排入原中央佇列：
狀態為 `WAITING_QUOTA`、checkpoint 有明確的額度原因、提出者仍在白名單、沒有待核准的需求變更。
一般 `AWAIT_HUMAN` 不自動執行。排程保存在 `quota_retry`（觀察時間、下次嘗試、次數），服務重啟後保留。

兩家供應商的措辭不同（實測樣本）：

| 供應商 | 原文 | 有時區？ | 排程 |
|---|---|---|---|
| Claude | `You've hit your session limit · resets 6:30pm (UTC)` | 有 | 以錯誤發生時間換算，該時刻加 2 分鐘 |
| Codex | 不同天：`You’ve hit your usage limit. … try again at Sep 15th, 2026 1:09 PM.`；同一天只有時刻：`… Try again at 1:09 PM.` | 訊息沒寫，但固定為 UTC | 該時刻加 2 分鐘 |

Codex 的訊息不標時區，但 Codex CLI 是以**執行它的機器的本地時區**輸出（codex-rs `protocol/src/error.rs` 的
`format_retry_timestamp` 用 chrono `Local`，2026-10-05 查 0.156.1 原始碼確認）。`CodexRuntime` 派工時以 `env TZ=UTC`
啟動 Codex（只影響 Codex 程序，不影響其他角色與專案測試），所以 `QuotaRetryTime` 一律以 UTC 解讀：
有日期就照日期；只有時刻代表 Codex 的「今天」，以觀察時間（UTC）的日期為準，早於觀察時間一小時以上才算隔天。
注意 0.156.1 用的是彎引號 `You’ve`，`QuotaExceeded.explicit` 會先統一成直引號再比對（2026-10-05 前只認直引號，
這種措辭會被當成一般失敗，不會進 `WAITING_QUOTA`）。

解禁時間在 24 小時之後時（`farBeyondBackoff`），排在解禁之後試一次，中間不反覆重試。
兩家都解析不出時間時，才用 30 分鐘起的退避（60、120、240，最長 360 分鐘）。
（2026-10-05 前 Codex 的時間視為時區未知，只取 UTC+14／UTC−12 的邊界，排程最多晚一天，Slack 原文照登。）

到期只嘗試原工作，不以額外模型呼叫探測配額、不購買或兌換額度；再次遇到額度上限才排下一次，
其他失敗走一般人工處理。排程時間不代表供應商已恢復。任務中止、結束或提出者被移出白名單即不再自動排隊。

## Slack 呈現

`QuotaMessage` 把兩個時間分開講：

```
任務 #1001 等待額度。
供應商指定解禁：10月7日（週三）21:09（台北時間，約 4 天後）（原文 Oct 7th, 2026 1:09 PM，UTC）
下次自動嘗試：10月7日（週三）21:11（台北時間，約 4 天後）
```

兩家的解禁時間都換算成台北時間，以口語格式呈現（`TaipeiTime.friendly`）：今天／明天／後天或月日（跨年才寫年份）、
星期、時刻，以及距離觀察時間多久（60 分鐘內寫分鐘、48 小時內寫小時與分、更久寫天；已過去的時刻不寫）；
括號附供應商原文，Codex 的原文另標「UTC」表示系統採用的時區。Claude 的 `resets 2:30pm (UTC)` 只給時刻，
以觀察到額度停止的時刻為準取下一個符合的 UTC 時刻（`QuotaRetryTime.utcReset`）。
原文有時間字樣但解析不了時照原文呈現並註明「無法解析，系統不推測」。「下次自動嘗試」也用同一個口語格式。
（2026-10-03 前 Claude 的 UTC 時間原文照登；2026-10-05 前 Codex 原文照登、時間格式為 `2026-09-16 09:11（台北時間）`。）
解禁時間很遠時，訊息會說明在那之前不再反覆重試，使用者也可在解禁後自行續跑。

## 手動繼續與重啟

- 「繼續任務」按鈕與自動排程共用 SQLite 條件更新，只允許 `WAITING_QUOTA` 轉為 `RESUME_QUEUED`；
  連按、重送或中止後的舊按鈕不會重複派工。
- 服務重啟後 `WAITING_QUOTA` 保留；尚未開始的 `RESUME_QUEUED` 退回 `WAITING_QUOTA`，再由自動排程或人工繼續。
- 已經排隊或執行中的配置式任務遇到服務重啟，仍採保守政策等待人工，不重播可能已執行的動作。
- legacy 的「重新開始」與續跑不同：先把舊工作區移到與 workspaces 同層的 `workspace-archives`，再建立乾淨 clone；
  封存失敗則停止。配置式模式不提供「重新開始」按鈕。

## 限制

- 沒有跨 runtime 接手：額度用盡不會自動改用另一個 CLI。
- 自動化測試使用假子行程與額度正反例，**未刻意耗盡真實訂閱額度**；真實額度恢復後的完整續跑以實際觀察為準。
