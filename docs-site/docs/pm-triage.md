# QA 受阻後的 PM 處理

## 分流做什麼

QA 受阻後會實際執行 `pm_triage`，沿用 PM 的 runtime、模型與 Slack 身分，
讀取原始需求、架構、測試計畫、實作、QA 報告及阻礙證據；不只是 tag PM。

- 既定範圍的實作或文件缺陷：PM 派 Backend 修正，再執行 QA 與已啟用的 Code Review。
- 原計畫缺少測試或證據：PM 派 QA 補驗證，再執行已啟用的 Code Review。
- 產品取捨、權限或外部環境問題：PM 列出具體問題與建議，停在 `AWAIT_HUMAN`。
- 舊版 remediation 自動修正最多兩輪。配置式 v2 則由受阻角色回報原因與證據，
  系統只能交給配置中的 `blocked`／`routes` 責任節點，每任務最多處理 6 個獨立受阻事件；
  每個事件最多通過 12 個節點。第一版留下的逐節點 key 會按證據合併，避免同一事件重複計額；
  無法辨識的舊格式仍保守保留原計數。
- 獨立事件額度用完後，停止訊息會提供一次性延長授權碼。原驗收負責人可在原討論串輸入
  `補充 #<ID> 核准延長自動交接 <授權碼>`，每次讓任務在目前已用次數之外再處理 2 個事件
  （接近上限時為剩餘數），事件總數最多 12 個；授權綁定
  目前配置、受阻證據與 HEAD，不重設歷史、不略過需求／計畫／PR 核准，也不能重放。
- QA 在 LIMITED 範圍補測試但不能 commit 時，系統先核對 diff 只含核准測試路徑，再交給
  配置中具 Git 寫入能力的 implementation 節點提交；不把 `.git` 寫權直接開給驗收 runtime。
  無法確定責任、需要擴權／人工決策或用完預算時明確停下，不會假裝有 agent 在背景處理。

目標節點若設有 `candidateRoles`，分流 agent 會依能力與阻礙選擇負責角色，並以 `handoff` 交付理由與工作。

「指定舊檔保持不變」已有內建 `compare-unchanged-files`；若計畫因不知如何比對而受阻，應交回 plan
補上路徑清單並保留原驗收要求，不應改派 requirements 請人刪除條件。其他工具能力缺口仍須明示具體缺口與處理者，
不以缺工具為由降低驗收標準。這是提示要求，既有已儲存決策不會自動作廢。
工作區內的環境設定／Compose／部署文件可以交合格角色處理；未授權的遠端主機操作仍需真人處理。

分流回報預設簡要，但必須列出來源節點、已確認原因、證據、責任角色與路由理由。
混合阻礙先路由可在現有範圍修正的項目，其餘阻礙保留到後續報告。

有 design 節點的內附配置，design 受阻也交給 triage（2026-10-10 起）；
明確回報 route=human 的產品決策仍交真人。設計受阻不再一律要求使用者處理。
尚未確認根因時，分流先查核或交合格角色定位；格式與一般建置錯誤不直接推論為缺少權限。
只有既有路線、權限與預算無法處理時才交真人。缺少前置設計／計畫時應先補齊，不得跳過前置閘門直接實作。
新路線只適用載入新配置的任務；已保存的快照不會自動更新。

所有原本的 QA、失敗報告、Code Review 與人工 PR 核准閘門仍保留。
PM 不得放寬驗收、消除未解的不確定性或自行擴權，修正完成也不會直接推送。
QA 的工作仍依原始情境測試計畫，不改成單純檢視程式。

## 同一討論串操作

在原討論串 **@主機器人**（不是只 tag PM 角色）：

- `處理 #編號`：讓等待人工的舊任務交由 PM 分析。
- `補充 #編號 你的答案`：把實際回覆帶入 PM 問題處理。

- `中斷 #編號`：只停下目前這一輪（與執行中狀態訊息上的「中斷這一輪」按鈕相同）。
- `開 PR #編號`：驗收負責人命令系統開 PR（與停止訊息的「開 PR」按鈕相同），條件與審查放行範圍見
  [review-gate](review-gate.md#負責人命令開-pr-與放行提醒等級2026-10-06)。

只允許白名單使用者、原頻道與原討論串，且必須已有 QA 計畫與 QA 結果。
佇列採原子狀態轉換，重複請求不會重複派工。不新建任務或重建工作區。
Slack 會區分「已排隊」、「PM 處理中」、「已派工」與「等待你回覆」。

### 需求本身有問題

- 新任務：測試計畫受阻會先交給分流（`plan.blocked = "triage"`）。分流判定是需求問題時用 route=requirements，
  並附 `human_decision`，停止訊息出現「核准：…」按鈕，負責人按下即核准該變更。
- 需求整理規則：只寫產品可觀察的行為；版本追溯、commit 差異、稽核、計畫覆蓋等流程證據由系統負責，不得寫成需求。
  不得自行刪除難以驗收的需求，但真人核准的變更要求刪除時照做並記錄。
- 任何任務（含舊快照）：停在測試計畫且已有需求基準時，停止訊息提供「需求要改」，
  需求負責人可直接送 `補充 #<ID> 核准需求變更 <要怎麼改與原因>`；系統回到需求節點重訂基準，
  之後設計、計畫、實作、驗收、審查照常重跑，計畫與 PR 仍需核准。非負責人或尚無基準時回白話說明。
- 「中斷這一輪」之後 runtime 交回的結果一律不採用（Codex 被停時可能以結束碼 0 交出半成品）；寫入範圍稽核照常執行，
  越界等安全例外不會被當成中斷而掩蓋。

### 承接時有未提交的修改

任務用完次數時，工作區可能留有「有寫檔權、沒有 commit 權」的角色（例如 LIMITED 驗收補的測試）的修改。
承接只帶走已 commit 的內容，所以停止訊息會列出這些檔案，並提供「保存未提交的修改並承接」：
系統先以工作區身分把它們 commit 到原任務（停用 repository hooks），再建立承接任務；新任務照常重新驗收與審查。
- 按鈕綁定訊息貼出當下的內容指紋；之後內容又變動就拒絕，請送 `補充 #id 狀態` 看最新清單。
- 保護路徑（`project.protectedPaths`）與 `.git` 一律不代為保存，請管理者處理。
- 只有驗收負責人可以操作；audit 記錄檔案清單與新 commit。

使用者操作被拒時，Slack 只顯示白話原因（`Diagnostics.forUser`）；例外類別與呼叫脈絡寫在 audit。

### 中斷這一輪 vs 中止任務

| | 中斷這一輪 | 中止任務 |
|---|---|---|
| 入口 | 執行中狀態訊息的按鈕，或 `中斷 #id` | 停止訊息／核准卡上的紅色按鈕 |
| 停掉的程序 | 本服務實例中該任務的 agent（`ai-team-<id>-*`）與系統驗證（`ai-team-check-<id>-*`）；設了 `AI_TEAM_INSTANCE` 時為 `ai-team-<實例>-<id>-*`、`ai-team-<實例>-check-<id>-*`，不影響同一台 VM 其他實例 | 同左 |
| 任務狀態 | `AWAIT_HUMAN`，可續跑 | `ABORTED`，終止；重啟時刪除工作區 |
| 次數與 session | 本輪已計次不重扣；「繼續執行」沿用原 session | 不適用 |

只接受配置流程中正在執行的任務；排隊、等人、角色對話與舊版管線任務會回覆說明、不做事。
中斷時 agent 若已交出結果，結果照常採用，停在下一步開始前。被停掉的驗證不會被當成程式失敗交回實作。
中斷旗標只存在記憶體，只對當下這一輪有效。

另有「負責人結案」：agent 的選項帶 `action=close` 時出現，只限驗收負責人、任務在 `AWAIT_HUMAN`。狀態同樣是 `ABORTED`，
但 audit 記 `OWNER_CLOSE`，重啟時**保留工作區**供負責人在系統外確認 PR（見 [plan-approval-buttons](plan-approval-buttons.md#由-agent-本人說明需要你決定的事)）。
結案後改變主意，仍可送 `開 PR #<id>` 讓系統開 PR（檢查沒過就維持結案）。

## 恢復與紀錄

`task_remediation` 保存目前階段、修正輪數與指示；`stage_attempt` 保留新增的每次階段產出，
原有 `stage_result` 仍保存最新一份。舊結果不會追溯補成歷次紀錄。
用量中斷走原有 checkpoint／繼續按鈕，續跑當前修正階段。
服務重啟時，執行中或排隊中的問題處理會停止並明示等待人工，不默默重跑。
若原工作區或 QA 稽核基準缺失，停止而不重建取代現場。

配置式 READ_ONLY 節點（例如分流）在任務已有 workspacePath 時查核該任務工作區，不改看主 repository；
workspace=false 只表示不建立新工作區。已保存路徑遺失、不符或為 symlink 時停止，不退回其他副本。
checkpoint 的原工作目錄與新目錄不一致時禁止 resume；已結束階段（activeNode=null）以新 session 重跑，舊 checkpoint／log 保留為證據。

### 隨時可改用新任務繼續

既有任務永遠使用建立時的配置快照，改進後的團隊規則只能透過新任務套用。
任務停下等人時，停止訊息一律提供「改用新任務繼續」（工作區有未提交修改時為「保存修改並改用新任務繼續」），
只有需求負責人能操作。新任務從最新 commit 接著做、改用目前配置，次數重新計算，需求、測試計畫與 PR 仍需核准。


## 服務建置的受阻與需求草稿修復

SERVICE 路線使用 service_triage，既定主機、操作與寫入範圍內的錯誤交回 Infrastructure 修正、重驗，不先送 QA 計畫。
真正缺少主機／憑證／權限或產品程式變更決策才停給人；[服務建置](service-delivery.md) 說明完整限制。
尚未建立需求基準、open_questions 為空且回報完成的需求草稿，若機械檢查發現 ID／欄位／原子驗收結構不合法，
引擎會交回 intake 自行修正，沿用既有自動交接上限。已有基準或真正待釐清的問題不套用；語意矛盾仍由 agent 查核。
