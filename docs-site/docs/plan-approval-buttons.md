# 測試計畫核准按鈕

## 行為

- 完整計畫的最後一頁以系統 App 發送兩個按鈕：核准測試計畫、要求修改。
- 按鈕 value 綁定任務、計畫節點、計畫 digest、配置與需求基準。
- 只允許白名單內的原負責人在原頻道／討論串、AWAIT_HUMAN 狀態操作。
- 核准成功保存收據並自動排入中央 QA 佇列，不需另送續跑；重複點擊不重複派工，PR 仍另行核准。
  只有目前等待中的對應 VERIFICATION 節點可核准並派工，不猜測其他節點的恢復路徑。
- 服務重啟後不會掃描或恢復所有已核准的等待任務；管理者要恢復特定任務時，於啟動時一次性傳入
  `AI_TEAM_RESUME_APPROVED_TASK=<任務編號>`（不寫進 env.sh，也不會代建核准收據）。
- 要求修改撤回該計畫核准並等待具體意見；下一則具體補充回到計畫節點，保留重試上限。
- 重新核准視為撤回修改要求；任何新計畫仍須重新核准。
- 專案配置 `project.autoApprovePlanWhenValid: true` 時，計畫若通過系統機械檢查（涵蓋全部原子驗收項目、
  每條情境有反例、操作契約可執行）就自動核准並直接派驗收，不貼按鈕卡；收據照常綁定 digest、配置與需求基準，
  稽核記為系統核准。未通過檢查仍走按鈕。預設 false；PR、需求變更與對外動作仍一律真人核准。
- 文字指令繼續支援。首尾反引號或 text 程式碼區塊包住的完整「補充／處理 #ID」
  指令會解開格式；不從一般問題、程式碼範例或段落中擷取指令。

## Slack App 注意事項

主系統 App 範本 `deploy/slack-app-manifest.yaml` 啟用 interactivity。
角色 App 範本目前 `is_enabled: false`，不可只因程式已註冊 handler 就宣稱角色按鈕可用。
因此卡片由主系統身分發送。程式同時註冊系統及角色 handler，供管理者另行啟用角色互動時使用。
不為此自動修改 Slack App 管理設定。

## 停止訊息的選項按鈕

任務停在 `AWAIT_HUMAN` 時，訊息會先用白話說「停下來了、沒有 agent 在跑、要等你決定」，
再列出目前狀態真的可用的選項（見 `HumanOptions`），能一鍵完成的做成按鈕（見 `HumanGate`）。

按鈕**不是新的權限路徑**：按下去送出的就是使用者本來要手動打的那串「補充」指令，
經過同一份白名單、同一套驗證，只是不必自己抄授權碼（曾發生授權碼被誤填成使用者 ID）。

| 選項 | 形式 | 說明 |
|---|---|---|
| 再給系統兩次機會 | 按鈕（primary） | 額度用完時才出現，value 直接帶授權碼 |
| 看完整報告 | 按鈕 | 唯讀，不改任務狀態；只在摘要模式出現 |
| 中止任務 | 按鈕（danger） | 沿用既有 `ai_team_abort` |
| 重新整理選項 | 按鈕 | 卡在重試上限、又沒有恢復方式時出現；送 `狀態`，不啟動 agent（2026-10-03 起） |
| 需求要改／告訴它還缺什麼／你自己修好了，請它重驗 | 按鈕＋輸入視窗 | 2026-10-03 起（`HumanInput`），見下節 |
| 核准測試計畫 | 計畫卡上的按鈕 | 停止訊息只說明「請用測試計畫卡上的按鈕」 |

- 按鈕只在「至少有一個可一鍵完成或可開視窗的選項」時才出現，避免每次停止都掛一排按鈕。
- 一則訊息最多 8 顆指令按鈕加中止（2026-10-03 前為 4；按鈕版面的文字不再附打字指令，按鈕被截掉就等於選項消失）；
  `HumanGate.Command` 的 value 超過 1900 字元會直接拒絕，不靜默截斷。
- **按鈕版面的文字不再教人打「補充 #N …」**（`HumanOptions.render(..., typed=false)`）。只有按鈕版面被 Slack 拒收、
  改送純文字時，才附上打字指令（`typed=true`）。打字指令本身仍然有效。

### 要填內容的選項：輸入視窗（2026-10-03 起）

`HumanInput` 為三種要寫內容的選項做按鈕（action_id `ai_team_human_input_N`，value＝`任務|種類`），按下後打開 Slack modal
（callback_id `ai_team_human_input_submit`）。送出後組成與打字**完全相同**的指令，經 `requestTriage` 走原本的驗證：

| 選項 | 視窗內容 | 送出的指令 |
|---|---|---|
| 需求要改 | 多行輸入「要怎麼改、為什麼」 | `核准需求變更 <內容>`（仍只有需求負責人能核准） |
| 告訴它還缺什麼 | 多行輸入 | `<內容>` |
| 你自己修好了，請它重驗 | **開窗當下**由系統查驗收節點與目前 HEAD 顯示確認，不必抄 commit | `核准人工修復重驗 <節點> <commit>` |

- 開窗與送出都只認白名單使用者與原討論串；視窗 metadata 只放任務、種類、討論串（與重驗目標），使用者不能改寫指令種類。
- 空白內容以欄位錯誤擋下，不會送出；`trigger_id` 只有 3 秒，開窗在 handler 內同步完成，送出後的處理才交給 ingress。
- 計畫卡按「要求修改」後的回覆也附「說明要怎麼改」（告訴它還缺什麼的視窗）。
- **Socket Mode 下的輸入視窗尚未在真實 Slack 實測**；主 App manifest 已啟用 interactivity，modal 不需新增 scope。

### 其他附按鈕的系統訊息（2026-10-03 起）

- 同串再 @主機器人、原任務在等你（`AWAIT_HUMAN`／`WAITING_QUOTA`）：附「查看目前可用選項」（送 `狀態`）。
- 計畫自動核准後：附「檢視測試計畫」。唯讀查看（`檢視測試計畫`、`檢視完整報告`）**任何任務狀態都可以用**；
  以前任務執行中一律被「不能新增續跑」擋下。已核准的計畫只顯示內容、不附核准按鈕。
- 操作被拒（例如承接時檔案已變動）且任務仍在等你：附「重新整理選項」。
- 角色本人貼的階段報告最後仍是文字「完整報告：補充 #N 檢視完整報告」：角色 App 沒開 interactivity，按鈕按了收不到。
- 只認任務原本的討論串；轉貼到別處的按鈕不會生效。
- 另一種按鈕不在停止訊息上：純詢問結束時的「開成新需求 N：短標題」（`SpinoffButtons`，action_id `ai_team_spinoff_N`，
  value 只放 `任務編號|序號`，原文由系統從任務紀錄讀回）。行為見 `docs-site/agent/operations.md` 的「建立任務」。
- 角色報告的顯示也同步白話化：`route` 翻成「交回工程實作修正（implementation）」這種形式，
  保留原鍵以便對照配置；`execution_status` 與 `verdict` 一併改為口語說法。

## 由 agent 本人說明需要你決定的事

待決事項若只寫在長 summary 裡，摘要模式只顯示前 500 字，使用者得另外去挖。因此所有角色共用的回報契約（`FailureReport`，執行期才加進 schema，既有任務也適用）新增必填、
可為 null 的 `human_decision`：

| 欄位 | 內容 |
|---|---|
| `headline` | 一句話說為什麼停下來 |
| `question` | 一次只問一件最需要決定的事 |
| `options[]` | 2–4 個選項；`label` 是按鈕文字，`consequence` 說選了會怎樣。只剩固定按鈕能處理時為空陣列（見下方） |
| `recommendation` | agent 建議選哪個、為什麼 |
| `also_needed[]` | 不是選擇題但也需要真人或維運去做的事 |

規則寫在契約指示裡：`route=human` 或阻礙須由真人／維運處理時必填，並一律用白話、不以節點代號或
SC／REQ 編號當主詞。

呈現：
- 角色本人的回報把決定事項放最前面、**完整顯示**，不受 500 字摘要限制；原本的摘要降為補充。
- 系統停止訊息只放問題與按鈕，註明「請看上方角色的說明」，避免同一段話貼兩次。
- 選項各自一顆按鈕，獨立一排；按下去送出「負責人決定：<問題>　選擇：<選項>（<後果>）」作為補充，
  交由流程重新判斷。以「負責人決定：」開頭，永遠不會被當成任何「核准…」指令。
- 都不合適時仍可直接打字補充。舊報告沒有這個欄位時維持原本呈現。
- 選項只能是「按下去流程就能照做」的事。流程沒有「結案」路線：結束任務、在系統外自行開 PR 後收尾、改用新任務繼續，
  都由停止訊息上的固定按鈕（「中止任務」「改用新任務繼續」）處理，契約禁止寫成選項；這時 `options` 給空陣列，
  `question` 說明要按哪顆固定按鈕。2026-10-06 加入（#1022 的「確認結案」類選項按了五次，每次都只是重跑分流後又停下）。

## 等待需求變更核准時的選項，以及自動處理次數用完時的說明

**等待需求變更核准**：triage 依使用者決定改派 `requirements` 後，系統只接受「核准需求變更 <內容>」。
這個狀態下選項按鈕直接送核准指令，按鈕文字寫「核准：…」，說明也明講按下去就是核准需求變更。
閘門擋下輸入時，會重新附上目前正確的按鈕。

**用完次數卻仍提供選項**：流程總次數超過上限、延長額度已達硬上限，且沒有已登記事件或恢復授權時，
任何選項都不會讓任務前進（兩種受控恢復授權在總上限用盡時也一律拒絕）。這時停止訊息改為直接說明
「這個任務已經無法再自動往下跑」、成果保留在哪個 commit，以及接下來需要人做的事
（另開任務並註明以此分支為基礎、由有推送權限的人推送並開 PR），不再提供看似可行的按鈕。
