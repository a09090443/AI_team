# ADR：受阻發現的傳遞連續性與被拒工具的可信度

日期：2026-09-15
狀態：已接受，尚未部署

## 背景

#1014 在 2026-09-15 12:57 再次停在 `AWAIT_HUMAN`。查核後確認不是崩潰、額度或部署問題：

1. 2026-09-14 15:43 review 節點回報 `REQUEST_CHANGES`，CONFIRMED HIGH：
   `MailServiceImpl.java:222` 以 `DeadlineSocketFactory` 覆蓋 SSLSocketFactory，
   預設 `overall-timeout=30000` 下正常寄送必走該路徑，隱式 TLS（465）退化為明文 TCP。
2. 該報告是受阻結果，`FlowEngine` 只在 `block == null` 時寫入 `flow.receipts`，因此沒有保存。
3. 受阻報告改 append 進 `flow.context`，但當時 `flow.context` 已達 20000 字元上限，
   而 `Diagnostics.clip` 是 `substring(0, max)` — 留頭截尾。`clip(已滿 + 新內容, 20000)`
   永遠等於原本的內容，**context 已永久凍結**，該報告整段被丟棄。
4. `lastBlockReason` 當時確實存過 review 的理由，但在下一個節點受阻時就被覆寫。
5. 今日 triage 因此只看到舊的 implementation npm 受阻與 verification 27/27 全 PASS，
   合理推論「查無可分派缺口」並 `route=human`。流程忠實執行了被截斷的輸入。

同一輪另有兩個放大問題：

- triage 使用的 coordinator 角色白名單是 `["Read","Grep","Glob"]`，完全沒有 Bash，
  但報告的證據段落寫了 `git log`／`git status`／`git rev-parse`／`git show --stat` 的輸出。
  系統只把工具遭拒記成一行稽核，沒有讓該報告失去可信度。
- triage 的 gate 是 `REPORT`，依設計不產生系統獨立驗證收據，提示中顯示為 `null`，
  被讀成「查無建置證據」，成為受阻理由的第二個支柱。

## 決策

1. **`flow.context` 改為滾動紀錄**（`FlowContext`）。單筆事件先截斷至 6000 字元，
   總量超過 20000 時以段落為單位淘汰最舊內容，並在開頭標示已淘汰。
   舊 context 沒有段落標記時退化為保留最新尾端。最新事件一定送得到下游。
2. **新增 `flow.blockedFindings`**，以來源節點為鍵保存未解除的受阻報告（因此筆數受配置節點數限制）。
   由 `ConfiguredExecutor` 無條件注入下游提示，不佔用 context 長度預算。
   只有該節點自己通過時才移除；需求變更不清除，採 fail closed。
3. **被拒工具與未受阻結論互斥**（`ToolTrust`）。本輪有工具呼叫遭拒、報告卻回報未受阻時判定受阻。
   這是機械檢查，不解讀報告文字：agent 會呼叫工具就表示它需要該工具，被拒後仍宣稱查核完成
   正是證據造假最容易發生的地方。已受阻的報告不受影響，合法引用被拒工具作為阻礙原因仍然可行。
   停止訊息會區分「角色完全沒有該工具」（配置與職責不符）與「有配置但呼叫方式不符白名單」。
4. **coordinator 補上唯讀 git 工具**（`git status`／`log`／`show`／`diff`／`rev-parse`），
   比照 inspector 的唯讀集合，讓 triage 的職責與能力一致。同時在 triage 提示明令
   證據只能寫本次實際執行成功的工具輸出。
5. **不產生收據的階段明講原因**，不顯示 `null`。

## 不做什麼

- 不放大自動交接額度，不改防循環上限，不新增任何繞過真人核准的路徑。
- 不自動判定受阻發現已解除；要解除必須有節點通過，或由後續報告說明原判定何處有誤。
- 不以文字比對猜測報告是否引用了被拒指令 —— 那會誤傷合法的受阻回報。

## 影響

- `flow.blockedFindings` 是新欄位，舊快照缺該欄位時為空 Map，不影響既有任務解析。
- 既有任務的 `flow.context` 若已飽和，新版第一次 append 就會淘汰最舊段落並開始正常運作，
  但**先前被丟棄的內容不會回來**；#1014 的 review 發現需靠 `blockedFindings` 之外的方式重新取得。
- 角色工具變更會改變配置版本；既有任務使用凍結快照，不會自動獲得新工具。

## 追加（同日）：停止訊息必須說明下一步

同一個缺陷類型還有第二個出口：系統知道自己在等哪一種決定、也知道有哪些人工指令可用，
但停止訊息只寫「請補充具體答案」。#1014 因此在 `AWAIT_HUMAN` 停了三天 ——
報告顯示「建議後續階段：human」，卻沒有任何地方告訴驗收負責人該送出什麼。

`HumanOptions` 依目前流程狀態列出真的可用的選項（需求變更核准、測試計畫核准、
人工修復重驗、一般補充、檢視完整報告），不列不適用的，並明講
「只寫『續跑』不會改變上一輪的判斷依據」與「停止不等於完成」。

## 修正（2026-09-16）：ToolTrust 過寬，誤判了成功的實作

原規則對所有節點套用，結果在 #1014 否決了一份真正成功的 implementation 報告：
它已 `SUCCESS`、`verify_passed=true`、提交 `fa96f9f` 且工作區乾淨，只因為中途為了 SC-18 的
重複量測跑了一次 `for i in 1 2 3; do mvn ...; done`——開頭是 `for`，不符合 `Bash(mvn *)`。

連鎖後果：報告只進 `blockedFindings` 沒進 `receipts` → verification 啟動前的前置契約檢查失敗 →
每次續跑都在任何 agent 啟動前報錯。而既有人工指令都排在這個檢查之後；`核准人工修復重驗`
另外會因流程總次數已超過上限（36／24）而被拒，還會清掉已核准的測試計畫。任務因此真的卡死。

判斷原則修正為：
- **主張型節點**（`READ_ONLY`：分流、需求、設計、計畫、審查）的產出就是主張，下游不會再查；
  工具被拒卻宣稱查核完成，證據基礎就不可信 → 維持 ToolTrust。
- **產物型節點**（`WORKSPACE`、`LIMITED`）的產出是 commit 與測試結果，有系統獨立驗證與審查
  再查一次；中途試了不在白名單的指令、改用其他方式完成是正常的工作方式 → 不套用。

### 恢復被誤判的前置契約：`核准恢復前置契約 <前置節點> <commit>`

`ContractRecovery` 把被系統規則錯誤否決、但本身合格的前置報告恢復成有效契約。
不重跑、不偽造，只有同時滿足下列條件才允許，而且只限驗收負責人：
- 該節點是目前節點的前置依賴，且目前確實缺少有效契約
- `blockedFindings` 有它的原始報告，並且**現在重新通過該節點真正的閘門**（真正失敗的報告不會因此被洗成有效）
- 節點不是 `READ_ONLY`（主張型產出不提供恢復，請重跑）
- 產物型節點的工作區乾淨，且 HEAD 等於授權時指定的 commit
- 寫入 RECOVERY 稽核；不重跑、不重設任何計數或核准

前置契約檢查遇到可恢復的情況時，改為停下來等人（附按鈕），不再丟成一般錯誤。
恢復後**不自動續跑**——通常還需要另一步決定，直接跑只會撞上上限、給出令人困惑的訊息。

### 「繼續執行」按鈕只在真的會前進時出現

`HumanOptions.resumeWillProceed` 同時要求：目前節點在本輪還沒做出判斷（沒有 receipt 也沒有
受阻發現）、前置契約都有效、驗收節點的計畫核准仍有效，而且「未達上限」或「有受控恢復授權」或
「同一受阻事件已登記且轉手站數未滿」。原樣重跑一個已經下過結論的節點只會得到同樣的結論——
#1014 反覆送「續跑」卻原地踏步，正是沒有人知道什麼時候續跑有用。
可以直接繼續時，不再同時推「延長額度」按鈕，避免多做一步、白用一次授權。

## 修正（2026-10-10）：一般指令失敗不等於工具拒絕

#1033 的 Codex `git diff --check` 因 SQL 檔尾空白行 exit 2，舊 ToolTrust 卻以
`command_execution` 不在角色工具白名單為由作廢設計報告。
現在 runtime 為這類事件標記 `COMMAND_FAILURE`，ToolTrust 不以它推論缺少工具權限；
FlowEngine 保留 RUNTIME_CALL 稽核與下游 context 證據。真正拒絕仍維持原檢查，
未解除的驗收失敗仍須 BLOCKED。bestpartner 設計受阻交 triage，沿用既有交接預算與前置閘門。
本項程式與配置修正尚待部署，既有等待任務不會因此自動續跑。
