# 操作與指令

## 誰可以操作

- 只有 `AI_TEAM_ALLOWED_USERS`（Slack user ID 白名單）內的真人可以觸發；bot 與團隊 agent 身分一律拒絕。
- 只在 `AI_TEAM_CHANNEL_ID` 指定的頻道生效；不支援 DM。
- 核准測試計畫、需求變更、PR 與「改用新任務繼續」只限任務提出者（驗收負責人）。
- 一則訊息只能 @一個團隊帳號，避免多個 App 重複派工。

## 建立任務

新 v2 任務啟用共用問題清單：已登錄的同目標問題由 agent 派修，完成前逐項檢查，
漏項不能以摘要宣稱完成。承接保留清單與歷史證據、重新驗收；明確唯讀請求仍只回答。
狀態回報區分本輪已驗證、待處理、範圍外／唯讀觀察；單項衍生任務會標示只涵蓋來源的部分項目。
討論串出現「問題清單格式不對，系統已請它自動修正重送（不計次）」是正常的自動修正，不需操作；同一步連續兩次格式錯誤才會停給人（2026-10-15 已部署）。
「交接（handoff）格式不對」也一樣，是 agent 指派下一階段角色時填錯格式，系統會附上可填的角色 ID 請它重送；角色名稱能唯一對應時會直接採用，不會出現這則訊息（2026-10-17 起）。
詳見[問題完整性](/docs/engineering-workflow#跨專案問題完整性2026-10-11)。這不表示系統能保證模型找出所有缺陷。

啟用自主派工的團隊會由 agent 依需求選擇下一階段負責人，Slack 顯示派工理由與交接工作。
例如 bestpartner 的環境設計與實作可選 Infrastructure；不需要你先猜角色名稱。
舊任務保留原派工快照，套用新政策請由負責人選「改用新任務繼續」，一般續跑不會換配置。
文件修改目前也會經過 QA 計畫與驗收：實作角色修改文件，QA 獨立查核內容與既定驗收；
純文件略過系統建置不代表略過 QA。2026-10-12 來源提示已按工作種類縮減不相關工作，並補文件站驗證與明確改派清單；2026-10-14 已部署 bestpartner 與 spring-starters（見[部署紀錄](/docs/deploy-2026-09-06-v2#2026-10-14-文件派工與角色提示修正)），流程節點數保持不變。
角色與工具的已知限制見[文件任務派工查核](/docs/configurable-team#文件任務的派工限制與已知問題2026-10-12-查核)。
「改用新任務繼續」只承接該任務的需求與成果，不會把來源問答的其他發現自動加入範圍。
例如 #1037 的第一項發現開成 #1038，再承接成 #1039，仍只處理第一項；即使載入新版提示，也不等於已派修其餘八項。
需要整批修正時，派工需求必須明列完整清單與已完成項目，不能只靠更新提示或承接單一修正任務。

在允許頻道 @主機器人並附上需求：

```text
@zipe-ai-team 在 base-spring-boot-starter 新增 SHA-256 工具方法
```

- 每個討論串只有一個工作任務；同串再 @主機器人 不會建立平行任務（**即使該任務已結束**）。**新需求請開新討論串**。
  系統回覆依原任務狀態而定：已結束（`COMPLETED`／`PR_CREATED`／`ABORTED`／`FAILED`）只提示改 @角色追問或開新討論串；
  `AWAIT_HUMAN`／`WAITING_QUOTA` 才附「查看目前可用選項」按鈕（等同 `補充 #<id> 狀態`）；其他狀態（執行中、排隊、等 PR 核准）不建議補充。
  同串追問可直接 @角色（唯讀角色對話，不受此限制）。
- 純詢問（intake 判定 `question`）會直接回答並結束（`COMPLETED`），不進開發流程。「已結束」只代表這次問答完成，
  不代表回答中提到的問題已處理。
- 文件維護請求（例如「確認系統建置的安裝文件是否有正確編寫」）查到有明確依據的文件錯誤時，intake 提示要求
  用 `implementation` 合併派修與驗證，不把同一目標內的修正逐項交給使用者開新需求。沒有問題則回答查核結果。
  明確要求只檢查不修改、或只是詢問運作方式時仍維持純詢問；產品取捨、新權限及未授權資料操作仍需釐清。
  此規則於 2026-10-11 部署至 bestpartner（配置 5263f682…），啟動與資料完整性檢查通過；模型分類尚待新任務實測，既有任務快照不會更新。
- intake 提示詞（`orchestrator/teams/prompts/intake.md`）要求 PM 在確定維持純詢問時，把回答過程發現的錯誤、文件與程式不一致、
  待修事項逐項寫進 `out_of_scope`（一項一件、可直接當需求），不可只在回答內文帶過；同一個錯誤出現在多個檔案時合併為一項，
  需要先做決定的項目句首標「需決定：」並列出選項；另在 `out_of_scope_titles` 為每項寫 20 字以內、彼此開頭不同的短標題
  （需決定的項目以「決定…」開頭，2026-10-04 新增）。這是提示詞要求，仍依賴模型遵守；
  直接 @角色 的唯讀對話沒有這個機制。
- 純文件／設定修改（例如改一行說明文件）照完整流程走：測試計畫與驗收以系統內建的 `inspect-content` 讀已提交的檔案判定，
  不需要專案配置額外操作。專案腳本（shell）不會被列為驗收項目，改由審查檢查。
- 需求要改實作角色寫不了的檔案（bestpartner 的 `.claude/rules/**`、`.claude/skills/**`）時，討論串會出現「先由 Backend Agent（codex）只修改這些檔案…
  其餘修改與建置測試接著由原實作角色完成」：同一輪實作分兩段，兩段都完成後才進驗收（分段改派，2026-10-04 起，見 multi-runtime）。
- 純詢問的回答若列了 `out_of_scope`（回答時發現、但唯讀詢問不能處理的事），任務結束後原討論串會多一則
  「回答時另外發現以下事項」，前 5 項各有按鈕「開成新需求 N：短標題」（標題超過 30 字截斷加「…」、反引號去掉；
  標題數量與項目對不上或該項沒有標題時只顯示「開成新需求 N」，舊任務也是如此）。訊息內文每項以粗體短標題開頭。按下後在頻道開新討論串建立任務：需求文字＝該項原文、
  需求負責人＝按的人、原問答摘要帶入交接紀錄；從 intake 照正常流程走，不沿用任何核准。同一項只會開一次，
  重複按會回覆已開立的任務編號；只認白名單使用者與原討論串。實作類任務的 `out_of_scope` 是刻意排除的範圍，不出按鈕。
- 需求不清楚或有產品取捨時，PM 會停下來問（`AWAIT_HUMAN`）。

## 在任務原討論串下指令

**任務目標行**（2026-10-15 已部署）：配置流程的停止訊息、`補充 #<id> 狀態`、狀態卡與承接後新討論串的第一則，
開頭固定一行 `🎯 <需求原文前 60 字>（承接自 #<原任務>）`，對話再長或換到承接討論串也看得出原本要做什麼。
只用已保存的需求原文，不呼叫模型；已貼出的舊訊息不會改寫（`TaskGoal`）。

**平常用按鈕即可**（2026-10-03 起）：停止訊息的每個選項都有按鈕；要寫內容的「需求要改」「告訴它還缺什麼」
「你自己修好了，請它重驗」按下後會跳出輸入視窗；訊息不再教你打字。以下打字指令仍然有效，是按鈕送不出去時的後備，
細節見 [plan-approval-buttons](/docs/plan-approval-buttons)。

以下指令都要在**該任務原本的討論串**內 @主機器人 送出，在其他討論串送出會被拒絕。
指令可以包在反引號或 text 程式碼區塊裡，系統會解開格式。`檢視測試計畫`、`檢視完整報告` 是唯讀，任何任務狀態都可以用。

| 指令 | 作用 |
|---|---|
| `補充 #<id> <答案>` | 回答 agent 的問題，續跑原快照節點 |
| `補充 #<id> 狀態` | 唯讀：重新貼出目前狀態與真的可用的選項，不啟動 agent |
| `補充 #<id> 核准需求變更 <怎麼改與原因>` | 需求負責人核准需求變更，回到 intake 重訂基準，下游全部重跑 |
| `處理 #<id>` | 讓等待人工的任務交由 PM 分流分析 |
| `中斷 #<id>` | 只停下目前這一輪（任務轉 `AWAIT_HUMAN`，可續跑）；等同狀態卡上的「中斷這一輪」按鈕 |
| `開 PR #<id>`（也可 `開PR #<id>`、`補充 #<id> 開 PR`） | 只限驗收負責人。等待核准 PR 時等同按核准；停下等人或已由負責人結案（`action=close`）時，發布證據有效就重新檢查（缺系統獨立驗證收據會先重跑）並直接推分支開 PR。審查只允許放行「已核准、沒有 HIGH、只因等級寫成 INFO 之類提醒」的項目；驗收只允許放行「其他條件全過、只剩未核實事項」（2026-10-08 起），PR 說明都會列出。審查還沒跑過時先補跑審查，通過就直接開 PR，有問題就停下。不符合時只回原因、不改狀態。等同停止訊息上的「開 PR」按鈕（2026-10-06 起） |

停止訊息上的按鈕，送出的就是對應的 `補充` 指令，走同一套白名單與驗證，只是免抄授權碼。
下列指令通常由按鈕產生，格式由系統提供，不需要手打：
`核准測試計畫`、`核准配置更新`、`核准恢復驗收 <驗收節點> <配置版本>`、`核准恢復前置契約 <前置節點> <commit>`。

## 按鈕語意

指定舊檔不得修改的檢查由系統提供版本比對，驗收失敗會交回實作修正，不需使用者逐檔確認。
舊任務已停在「等待需求變更核准」時，部署不會替你撤回或核准該決策；可由負責人按「改用新任務繼續」，
重新規劃時明確保留舊檔不得修改的要求。已開始實作但沒有固定比較基準的舊任務，不會以當前版本補造證據。

需要你決定時，角色應先說清楚目前做到哪裡、為何停下、各選項對原需求的影響與建議。
技術編號與證據放在補充；減少檢查或改由審查把關時，必須明說少了什麼保證。
這是新回報的提示規則，既有訊息不會自動改寫。

| 按鈕 | 出現時機 | 結果 |
|---|---|---|
| 核准測試計畫／要求修改 | 測試計畫最後一頁 | 核准後自動排入 QA；要求修改會等你的具體意見 |
| 核准：… | agent 以 `human_decision` 提出選擇題 | 依所選選項繼續 |
| agent 的選項按鈕 | agent 以 `human_decision` 提出選擇題 | 依選項 `action`：`decide` 交回流程重新判斷；`close` 由系統直接結案（`ABORTED`、只限驗收負責人、**保留工作區**）；`successor` 同「改用新任務繼續」；`publish` 同「開 PR」（證據不符合時不出現） |
| 開 PR | 停下等人且發布證據有效時 | 同 `開 PR #<id>` 指令：只限驗收負責人，重新檢查後直接推分支開 PR，不必再按核准 |
| 繼續執行 | 只在真的會前進時出現 | 沿用原 session 續跑 |
| 中斷這一輪 | 執行中狀態卡 | 停掉本任務 agent 與系統驗證程序，任務保留；2026-10-20 來源新增對原 pending job 的取消要求，尚未部署，見下方長作業恢復 |
| 中止任務 | 停止訊息／核准卡（紅色） | 任務 `ABORTED`，下次服務重啟時刪除工作區 |
| 改用新任務繼續 | 任務停下等人時 | 在新討論串開新任務，從原分支最新 commit 接著做、套用目前配置、次數重算；**不沿用任何核准** |
| 保存修改並改用新任務繼續 | 工作區有未提交修改時 | 先代為 commit 可歸責的修改（不含保護路徑與 `.git`），再開新任務 |
| 檢視配置更新 → 核准配置更新 → 重新執行這一步 | 管理者部署修正配置後，送 `補充 #<id> 狀態` | 受控把舊任務遷移到新配置 |
| 核准，推分支並開 PR | `AWAIT_PR_APPROVAL` | 發布前重新檢查 commit、工作樹與分支，才推分支開 PR。按下後狀態立刻變成 `PUBLISH_RUNNING`，工作仍排進共用中央佇列。系統先確認收到核准，再由中央佇列列出實際執行中與前方排隊任務（含角色對話）；輪到時通知開始這一輪工作。狀態為發布中不代表推送已開始。失敗（例如 token 未設定）時留在 `AWAIT_PR_APPROVAL` 並貼出原因，修好後再按一次 |
| 重新進入核准 PR | 停在發布核准（approval）節點的 `AWAIT_HUMAN` | 重新檢查證據、commit 與工作區，通過才重新貼出核准按鈕；不推送、不呼叫 agent（送出的指令同「續跑」） |

額度用盡（`WAITING_QUOTA`）會依供應商給的解禁時間自動續跑，不需按鈕，見 [quota-continuation](/docs/quota-continuation)。
停止訊息標題為「AI 服務帳號無法使用」時，是 VM 上 Claude Code／Codex 的帳號被組織停用或登入失效，不是任務內容問題；
由帳號擁有者在服務主機重新登入或請組織管理者開放權限後，再按原本的「繼續執行」。此情況不自動續跑，次數已還原（2026-10-14 已部署，見 [失敗回報](/docs/failure-reporting#帳號或登入被供應商拒絕provideraccessdenied)）。

## 直接對角色說話

```text
@QA Agent 這次 SMTP failover 還需要哪些測試情境？   ← 唯讀對話，不執行、不改檔
@Backend Agent 執行 新增 SMTP failover            ← 「執行 」前綴才是派工
```

- 一般文字一律視為對話，包括「幫我改」；派工必須用 `執行 ` 前綴。
- 在沒有工作任務的新討論串派工，會交給原本的 PM 管線；在既有任務討論串派工，交給該任務的分流，不另建平行實作。
- 對話是獨立唯讀子請求：只准 Read／Grep／Glob，不能 commit、派工、核准或取代 QA／Review 證據。
- 前提是角色 App 已設定 Socket Mode 與 App-Level Token，見 [direct-agent-requests](/docs/direct-agent-requests)。

## 基準驗證（2026-10-18 起）

```text
@主機器人 基準驗證   ← 在頻道任何地方送出；不建立任務
```

- 在基準分支最新 commit 的全新 clone 跑一次配置的驗證指令，確認它們在**還沒有任何修改時**能不能通過。
  結果另開一則頻道訊息，逐條列出通過／程式失敗／環境缺件／逾時與紀錄路徑。
- 服務啟動時，若「目前配置版本＋基準 commit」還沒有結果，會自動排一次（接入新專案、部署新配置都會觸發；只換 JAR 不重跑）。
  `AI_TEAM_BASELINE_VERIFY=off` 可關掉自動觸發。
- 走中央佇列，不與任務同時執行；佇列通知顯示「基準驗證」。
- **不通過只警告、不阻擋任務**：之後新任務開始時討論串會提醒一次，每個節點的 agent 也會收到「已知基準失敗」的系統事實。
  修好配置、環境或 repo 後再送一次「基準驗證」確認。詳見 [基準驗證](/docs/baseline-verification)。

## 維運指令（在服務主機上）

### 任務排隊通知（2026-10-12）

中央佇列在受理新任務、承接／衍生、續跑、計畫核准、角色對話與發布工作時，會在該任務討論串回報：
目前正在執行的任務編號，以及前方排隊任務的實際順序。輪到時再通知「輪到任務 #N，開始執行這一輪工作」。
此訊息是排入當下的狀態，不是持續更新的看板，不提供無法確定的等待分鐘數，也不需要重複送出。
前方工作結束這一輪、暫停等人或等額度，就會釋放中央工作迴圈；不必等到 PR 合併或產品完整交付。2026-10-20 來源新增的長作業等待例外：只釋放模型程序，仍占中央執行槽，直到對帳後接續或停下。
名單包含同一實例實際排入的角色對話／發布工作；已中止且尚未執行的工作不列為等待對象，也不發開始通知。
不同實例互不列入；只顯示編號、不顯示其他任務的需求內容。通知失敗會記錄日誌，仍保留工作排程。
本次修改不增加平行執行數；目前中央工作迴圈仍依序執行，不能僅調高 maxConcurrency 就視為整個管線已平行化。
2026-10-12 已部署 bestpartner 與 spring-starters；既有等待任務在重新排入時也適用。
完整程式測試與啟動檢查通過，Slack 新通知的真實端對端送達尚未實測，見 [部署紀錄](/docs/deploy-2026-09-06-v2#2026-10-12-中央佇列等待通知)。

`deploy/bootstrap/` 的腳本安裝後位於 `AI_TEAM_HOME`（通常是 `~/ai-team`），從那裡執行：


### 長作業自動接續與舊任務恢復（2026-10-20 來源已實作）

看到「工具仍在執行，系統會追蹤原作業並自動接續」時，不需重送任務、重啟 VM 或再核准。工具預設 30 秒交回 OPERATION_PENDING，模型以 BLOCKED 結束本輪，中央流程等待可信 journal 後續同 activeNode，不新計次；同實例後方任務仍排隊。未知／到期不表示成功，系統不能無限重開模型。

模型 timeout 只有在本次 sandbox cgroup 已確認清理（RuntimeTimedOut、MODEL、cleanup=CONFIRMED）後才可自動對帳；獨立部署 executor 和遠端 job 不會因此被殺。真人按「中斷這一輪」會要求取消原 pending job，任務仍保留；明確中斷不是暫時釋放模型。取消未確認不宣稱遠端停止。

服務本身重新啟動後，有同 HEAD 有效 journal 的原執行中／RESUME_QUEUED 任務可經中央佇列自動接回；沒有 journal 的任務仍依既有中斷規則等人。此為應用恢復邏輯，不表示 orchestrator 已設定開機自啟。

舊 AWAIT_HUMAN（如 #1048）由管理者先透過固定 executor 的 --reconcile 核實原目標收據、HEAD 與來源 digest，再只於一次啟動設定 AI_TEAM_RESUME_OPERATION_TASK 為單一任務編號；要求乾淨工作區、原 activeNode 與有效同來源 journal。這不是 Slack 指令，也不會核准新計畫或 PR；用後移除變數，不直接改 DB 或偽造成功。步驟與 #1048 禁止重建的證據見[直連部署](/docs/direct-ssh-deployment)。

上述恢復來源尚未部署，模型逾時、重啟、自動續跑及取消的真實端對端未完成；不要把舊版網頁 HTTP200 當成這次恢復已驗收。
