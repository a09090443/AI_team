# 架構決策紀錄（Codex 與 Claude Code 共用）

> 只追加，不覆蓋。每則寫「決策／理由／影響」，並註明日期與提出者。

## 2026-09-27：AI 工具設定單一來源（Claude Code，使用者要求）

決策：規則只寫 `AGENTS.md`（CLAUDE.md 僅 `@AGENTS.md`）；skills 單一來源 `.agents/skills/`；MCP 單一來源 `.agents/mcp.json`；
各工具專屬檔由 `.agents/sync-agent-config.mjs` 產生並提交，docs-site prebuild 以 `--check` 防止手改漂移。
理由：`AGENTS.md` 與 `.agents/skills` 是最多工具原生支援的位置；Claude Code 只讀 `.claude/skills`、各工具 MCP 格式不同，
以產生檔補齊差異。未用 symlink：Windows 需要特殊權限（本機 Maven 測試已因 symlink 權限失敗過）。
影響：Cursor、opencode 會同時讀到 `.agents/skills` 與 `.claude/skills` 的同名 skill，內容由腳本保證一致。
`.codex/` 不進版控，其他開發者需各自執行同步。本機 `dbx` MCP 是否屬於專案共用尚未確認，未納入共用來源。

## 2026-09-27：文件優先規則與機械驗證的專案目錄樹（Claude Code，使用者要求）

決策：所有 agent 工作一律先讀文件；文件缺漏或與程式不符時必須在同次工作中修正文件。
專案目錄樹 `docs-site/agent/project-tree.md` 由 prebuild 檢查與實際檔案比對，主程式、團隊配置、prompts、schemas、
deploy 與 docs-site 的每個檔案都必須列入。
理由：讓 agent 以文件為基礎快速定位，並以機械檢查落實「程式存在但文件沒寫就要補」，避免目錄樹逐漸過時。
影響：新增、搬移、刪除上述範圍的檔案時，必須同步更新目錄樹（含用途說明），否則 docs-site build 失敗。
檢查只驗證檔案有列出與路徑存在，不驗證說明文字是否正確；內容正確性仍靠規則與人工核對。

## 2026-09-27：文件移入 docs-site/docs/，根目錄不再有 docs/（Claude Code，使用者要求）

決策：取代下方「docs/ 留在原位」的做法。所有文件移到 `docs-site/docs/`，根目錄 `docs/` 刪除；
repo 內對 `docs/xxx.md` 的引用全部改為 `docs-site/docs/xxx.md`。
理由：使用者要求文件統一整理在 docs-site，不保留兩個文件位置。
影響：新文件一律放 `docs-site/docs/` 並登錄 `catalog.mjs`；文件中連到 repo 其他檔案的相對連結需 `../../`；
新機來源打包需包含 `docs-site/docs` 與 `docs-site/agent`（不含 node_modules／build）。
歷史紀錄（`.ai/`、HANDOFF 等）中的舊 `docs/` 路徑保留原樣，閱讀時自行對應到 `docs-site/docs/`。

## 2026-09-27：文件網站以 AI agent 為主要讀者，文件狀態集中登錄（Claude Code）

決策：`docs/` 留在原位不搬移；在 `docs-site/` 新增 agent 入口頁（`agent/`）與文件目錄資料 `catalog.mjs`，
由 catalog 產生 sidebar、`/catalog` 頁與 `llms.txt`／`llms-full.txt`，並在 prebuild 機械檢查 catalog 與 docs/ 一致。
理由：docs/ 被 AGENTS.md、Java 註解、prompts 與部署腳本以路徑引用，搬移會打斷約 30 處引用；
agent 最需要的是「哪份文件現在有效」與「做某件事該讀哪份」，把狀態集中在一份資料比在 42 份文件各自加 front matter 更不易漂移。
影響：新增或刪除 docs/ 文件必須同步更新 `docs-site/catalog.mjs`，否則 build 失敗；文件狀態改變（例如被取代）時也要改 catalog。
`llms.txt` 連結使用 config 的 `url`，目前為 localhost，部署前需改。

## 2026-09-10：opencode 作為第三個 runtime，能力宣告只寫實測過的

決策：接上 opencode CLI（id=opencode），四項能力全部先實測再宣告，未測的一律不列。
理由：能力宣告是呼叫端決定要不要降級的依據；宣告成有而實際沒有，失敗樣態是
「安靜地少做事」而不是報錯 —— 那比少一個 runtime 糟得多。
影響：opencode 是目前唯一會回報實際金額（step_finish.cost 逐 step 累加）的 runtime，
接的是 API key 供應商而非訂閱制，誤設貴模型的代價是直接的；模型名格式 `provider/model`
與另外兩家不通用，換 runtime 必須一併換掉 `AI_TEAM_MODEL_<角色>`。
用法錯誤的判定不共用 codex 那份（clap 結束碼 2），另開 yargs 版本。
VM 沙箱下的端對端執行與 Linux 狀態目錄位置尚未驗證，文件已明確標示，不得當成已支援。

## 2026-09-09 — 本機測試隔離、文件副本與有界恢復

以顯式 localTestNetwork opt-in 對齊 Codex 內層與外層 policy；命令網路採空 domain
allowlist 的 proxy 隔離，允許 namespace 內測試，不開放外部直連／主機既有服務。
文件採 target/qa-docs 的 HEAD 副本建置，避免可清理工具與唯讀 bind mount 衝突，
不開放原 doc-site 寫入。離線快取缺失即停止，不自動擴大網路權限。
已核准的能力遷移可再由原負責人明確授權該配置一次驗收；歷史次數保存、總上限不繞過，
且須重新核准計畫。部署與配置核准本身皆不授予額外重試，避免無限循環。
本輪安全審查拒絕 Slack 發送後僅做目的地唯讀核對，再審仍拒絕，未另找管道繞過。

## 2026-09-09 — 未呼叫模型的執行失敗不計入流程次數

決策：CLI 用法錯誤（事件流為空、結束碼 2、stderr 有用法字樣三者全中）視為
「本輪沒有任何 agent 工作發生」，還原該輪的節點 visits、transitions 與一次性
受控恢復授權，不與 `QuotaExceeded` 共用類別。

理由：防循環上限與一次性恢復授權是拿來擋「agent 反覆做同一件事」的，
不是拿來擋我們自己組裝參數的缺陷。#1014 就是被一個 `-P` 參數吃掉一次真人
授權，逼使用者重走整套配置遷移與核准。判定條件刻意保守，寧可多算一次，
也不要把真實的產品失敗洗掉。

代價：判定條件依賴 CLI 的用法錯誤文字與結束碼，CLI 改版可能失效；因此另加
opt-in 的真實 CLI 契約測試（零模型呼叫）同時驗證兩個子指令的參數，
不再只靠預檢通過就相信派工會成功。

## 2026-09-10 — 供應商時間原文照登，只取邊界不猜時區

決策：供應商回報的解禁時間一律以原文呈現，不換算、不推測時區；只有系統自己排定的
時間才換算台北並格式化。排程遇到沒有時區的日期時，用「最早 UTC+14／最晚 UTC−12」
兩個邊界推理，而不是假定某個時區。

理由：Codex 的 `try again at Sep 15th, 2026 1:09 PM` 沒有時區，誤差可達 ±14 小時。
猜錯的兩種後果都不能接受——猜早了反覆撞牆，猜晚了白等半天。用邊界推理則可以在
不猜的前提下，安全回答「是不是遠到不值得反覆重試」這個唯一需要回答的問題。

代價：解析依賴供應商的英文措辭，改版可能失效；因此判斷不出來時一律退回原有退避，
不讓解析失敗變成不重試。

## 2026-09-13 — resume 的執行選項屬於子指令

決策：`codex exec resume` 的 permission profile、sandbox、schema、model 與 reasoning
選項全放在 `resume` 之後、session id 之前。一般 workspace-write 續跑不用
父層 `-s`，改用 resume 可解析的 `-c sandbox_mode="workspace-write"`。

理由：CLI 會接受放在父層的 `-c`，但 session 證據顯示 resume 實際未套用，
會靜默退回 `:read-only`。這種失敗有 JSONL 與模型輸出，不會命中
`RuntimeUsageError`，必須從命令組裝根治。

## 2026-09-13 — 角色對人回覆預設簡要，完整證據另存

決策：Slack 平常只顯示判定、摘要、關鍵阻礙與下一步；受阻與防循環
也不直接貼逐情境報告。直接角色對話預設簡要、顯示最多 1200 字，
使用者明確追問時才展開。完整結構化報告仍保存於 `stage_result`，
不因顯示簡化而刪除證據或改變流程判定。

理由：預設完整貼出數千字會淹沒需要人處理的訊息；將顯示層與證據儲存分開，
可同時保留可追查性與簡潔操作體驗。
## 2026-09-13 — 人工修復後重驗以配置、節點與 commit 綁定

- 配置遷移恢復仍維持同 revision 一次，不放寬原本的防循環契約。
- 新增獨立的人工修復重驗：只允許原驗收負責人、乾淨工作區、不同於前次驗收的 HEAD，
  且同一 `configuration:node:commit` 永遠只能授權一次。
- 授權不清空 visits／transitions，仍需重新核准原測試計畫；流程總上限不解除。
- 若 CLI 在呼叫模型前即拒絕參數，才還原該次 grant 與 key，避免系統缺陷吃掉真人授權。
- 舊 FlowRun 沒有 `attemptHeads` 時，以保存的 `beforeHead`，再以驗收前置節點 `heads`
  作相容判定；新執行會持久化各 workspace 節點的 attempt HEAD。

## 2026-09-13 — 郵件整體逾時與失敗資訊去敏

- 每次寄送以單調時鐘計算剩餘整體時間，複製候選 sender 並縮限 connection/read/write
  timeout；不修改共用 sender，避免併發請求互相覆寫設定。
- 日誌與對外 suppressed chain 只保留伺服器標籤及例外類型，不保存 SMTP 伺服器回傳的
  原始訊息或 cause，避免認證資訊被回顯。
- 不以背景 Future 強制取消寄送，避免逾時後工作執行緒仍可能完成寄送而產生重複郵件。

## 2026-09-13 — 規畫採原子驗收與反例契約

- 新需求將概括的 `acceptance` 拆成有 ID 與維度的 `acceptance_items`；量詞涵蓋的操作、
  角色、輸入、狀態與失敗模式必須分開列出。
- 測試情境以 `acceptance_ids` 逐項追溯，並寫出 `counterexample`；系統拒絕遺漏、跨需求
  錯接或沒有反例的計畫，QA 與 Reviewer 也必須確認實際測試能使反例失敗。
- 舊任務沿用快照中的舊 schema／prompt；不自動改寫歷史計畫，避免進行中任務失效。

理由：只檢查 requirement ID 是否出現在任一情境，無法發現「全部方法」只測代表性方法，
也無法區分整體逾時與單次 socket 逾時。原子維度提供可機械查核的最小覆蓋單位，反例則迫使
規畫者說明測試辨識力；語意正確性仍需 Reviewer 查核。

## 2026-09-14 — Runtime 邊界轉換 Codex Schema，不改寫任務快照

- 完整團隊契約與歷史快照保持不變；送入 Codex Structured Outputs 前，僅在副本遞迴移除
  已知不支援的 `uniqueItems`。
- 陣列唯一性繼續由 `Traceability` 的確定性閘門執行，不把 API 相容性限制變成驗收放寬。
- `invalid_json_schema` 若發生在 `thread.started`／`turn.started` 之前，視為系統請求契約錯誤，
  還原該輪流程計數與一次性恢復授權；agent 已啟動後的失敗仍正常計次。

理由：舊任務快照不可竄改，但第三方 runtime 僅支援 JSON Schema 子集合；相容轉換應位於
runtime 邊界，業務語意則由本系統自己的可測閘門維持。

## 2026-09-14 — 受阻責任交接有獨立預算，驗收操作必須事前綁定

- 一般 `visits` / `transitions` 不清零；有受阻證據且配置明確指向責任節點時，
  每個任務可用最多 6 次不可重放的自動交接。
- 交接不能新增角色、操作、寫入範圍或核准；`human`、需求變更、計畫與 PR 核准仍停給真人。
- 新測試計畫情境必須引用配置給 verification 的 `operation_ids`；未知或未授權操作由系統拒絕。
- v2 獨立驗證改在 QA 前執行，QA 與 Reviewer 共用綁定 HEAD／baseline／configuration 的收據。

理由：受阻後的責任若已明確，不應因過去造訪數而必然卡住；但不限次數或由 agent
自行指定角色／命令會破壞安全邊界。操作契約與 QA 前系統收據讓權限缺口在規畫時就可被發現。

## 2026-09-14 — 自動交接以受阻事件計額，QA 測試變更交由 builder 提交

- 每任務最多 6 個獨立受阻事件；同一事件沿配置流程最多 12 個節點，不逐節點重複消耗事件額度。

  `protectedPaths`，系統依 blocked 分流節點的 `implementation` route 交給 WORKSPACE builder。
- 無安全配置路由、混入產品／保護路徑或路徑無法稽核時仍停給真人，不推測責任或擴權。
- 綁定 HEAD／需求／配置且 exit 0 的系統獨立驗證收據，是固定完整建置操作的主要證據；
  QA 不得因自身 operation 清單沒有重複同一命令而宣告受阻。

理由：QA 必須能補負向測試，但不應因此取得 Git metadata 寫權；提交是 builder 的責任。
事件與節點跳轉分開計數，才能同時容納正常返工鏈並保留確定的防循環上限。
## 2026-09-15 — 自動交接舊計數正規化與人工有界延長

- 第一版 `automaticHandoffKeys` 的 `<證據>:<節點>:<次數>` 是逐跳紀錄；新版事件制不得直接沿用
  其筆數。執行任務前將相同 64 位證據雜湊合併為 `incident:<證據>`，並留下 RECOVERY audit。
- 只有舊計數等於原 key 數、且每個 key 都可辨識時才重算；未知格式或缺 key 時保留較高舊值，
  避免遷移意外放寬防循環限制。#1014 的 6 筆可辨識 key 因此應合併為 4 個獨立事件。
- 基本事件上限仍為 6，不直接放大。額度用完時，停止訊息提供綁定配置、受阻證據與 HEAD 的
  一次性 token；只有 acceptanceOwner 可每次增加 2 個事件，最多額外 6 個，且 token 不可重放。
- 人工延長不重設 transitions、visits、handoff hops、事件歷史、需求／計畫核准或 PR 閘門。
  一般流程歷史次數與事件／跳轉上限分開呈現，避免把受控越界誤讀成計數故障。

## 2026-09-15 — 受阻發現的傳遞連續性與被拒工具的可信度

- `flow.context` 改為滾動交接紀錄：單筆事件上限 6000、總量 20000，超量淘汰最舊段落並在開頭標示，

  無條件注入下游提示、不佔 context 預算，只有該節點自己通過才移除；需求變更不清除，採 fail closed。
- 本輪有工具呼叫遭拒、報告卻回報未受阻時直接判定受阻。這是機械檢查、不解讀報告文字：
  會呼叫工具就表示需要它，被拒後仍宣稱查核完成不可採信。已受阻的報告不受影響。

理由：防循環與真人閘門都不該靠「下游看得到上游發現」這個隱含假設；證據一旦可能被長度上限

## 2026-09-18 — 自主程度：只在真人獨有的事情停下

理由：#1014／#1016 多數停頓都是系統自己能判斷的事，每次停下都要使用者介入，違背「團隊自動完成」的目的。
